# Audit — 2026-09-23: the pipeline, the gates and the terminal

**Scope — and its boundary.** This audit covers every *unfrozen* surface: the scheduled
job and its workflows, the ledger writers and what is committed, the gates, the
artifacts' provenance, and the page that reads them. It does **not** audit the frozen
model — score construction, factor definitions and bounds, weights, tiers, the
qualification gate, basket construction and the inference vocabulary — and it changes
none of them. `SPEC_HASH` is `91bbc2a7e466` before and after, parity is unchanged, and
the deferred register's triggers stand as written. Where reading an unfrozen surface
exposed a defect *in* a frozen one, it is recorded in §6 with evidence and left for
review, not fixed. "Audited" in this document means the unfrozen surfaces only.

**Method.** The committed ledger was validated as-is. The failed nightly runs were read
from their Actions logs. The full suite was run against `main` as the baseline:
**943 passed, 4 failed**. `nightly.main()` was run offline with the network stubbed,
and the terminal was driven in headless Chromium against CoinGecko payloads that were
stubbed, hostile or throttled. Every finding below that says *reproduced* was.

## 1. Found broken on `main`

### 1.1 Two artifacts were never committed — the board ran on a stale transport for six nights

`ledger/perp.json` (Phase 1.6, 2026-09-17) and `ledger/walkforward.json` (Phase 4,
2026-09-18) are written by `nightly.py` every night and validated on the runner by
`validate_ledger.py`. But `nightly.yml`'s Commit step stages an explicit allowlist, and
neither file is on it. Both died with the runner every night.

- **Effect.** `perp.json` has no browser fallback by design, so since 2026-09-18 the
  terminal has withheld the funding overlay from every row. The page prints "Leverage
  overlay unavailable — dated 2026-09-17", and the live ranking disagrees with the
  published one.
- `walkforward.json` read "3 nights" while the cross-section held 7. The deferred
  register calls it "refreshed every night".
- Run against the committed tree, `validate_ledger.py` fails on both files. It only ever
  ran on the runner's tree, before the files were discarded.

**Fixed.**
- Both files are staged.
- `tests/test_nightly.py` asserts that every entry under `ledger/` is named by the
  Commit step. It fails on the old workflow and names both files.
- The Commit step fails the run, after pushing, if anything under `ledger/` is still
  modified or untracked. That catches the next new artifact on its first night rather
  than six nights later.

### 1.2 An RWA paging overlap lost two whole nights of the crypto ledger (2026-09-21, -22)

- `rwa.fetch_markets` pages `/rwas/markets` by market cap, seconds apart. A name that
  moved up a rank between two requests was served on both pages: `quanta-services` on
  09-21 and `fiserv` on 09-22.
- The repeat reached `rwa_flow.csv`, `rwa_observed.csv` and `rwa_wrappers.csv` as
  duplicate keys.
- The single ledger gate refused them, so nothing was committed. That included a
  crypto ledger with nothing wrong in it.

**Fixed, at both layers.**
- `fetch_markets` keeps the first occurrence of each id and says in the feed detail how
  many repeated. The same rank shift can push a different name off both pages, so the
  count is reported rather than absorbed.
- The two models no longer share a verdict. `validate_ledger.py --scope crypto|rwa`, and
  the nightly takes the RWA verdict first, as a non-blocking step:
  - **RWA refused:** tonight's RWA files are restored from `HEAD`, the crypto ledger
    commits alone, and the run is failed at the end.
  - **Crypto gate refused:** the RWA rows commit alone, under the same
    "only `ledger/rwa*` may be staged" guard `rwa_release.yml` uses. `rwa_flow.csv` is
    the one series no key bought later can re-fetch.

### 1.3 The Selection Edge panel counted a three-day return as a one-day leg

`_edge_legs` paired *consecutive recorded* nights. With 09-21 and 09-22 missing, 09-20 →
09-23 entered the "one-day" IC as a three-day return. `_ic_legs`, which feeds the IC
matrix, already required the exact calendar offset and dropped that leg. So the same
cell was published twice with two values:

| | legs | mean IC | 95% CI |
|---|---|---|---|
| Edge panel (before) | 47 | −0.0653 | [−0.1134, −0.0171] |
| IC matrix / edge panel (after) | 46 | −0.0595 | [−0.1074, −0.0117] |

`tests/test_ic_matrix.py` was the failing test that caught this on `main`.

**Fixed.**
- `_edge_legs` now requires `iso_day_diff(a, b) == 1`. It is not a captured function,
  so the hash does not move.
- The state is unchanged. The interval still lies entirely below zero, so the board's
  vocabulary stays withdrawn exactly as before.
- A new test recomputes both estimators from the ledger on disk and asserts that they
  count the same legs.

### 1.4 Three tests were red on `main`, and nothing ran them

Besides §1.3:
- `test_walkforward` and `test_ic_provenance` failed on the stale `walkforward.json`
  (§1.1).
- `test_xsec` asserted that the `clamped` column is non-empty. It is empty by
  definition when no raw score leaves [0, 100], which has been every night since the
  stale overlay was removed.

Nobody saw these, for two reasons. The nightly's own commits trigger no workflow (a
`GITHUB_TOKEN` push starts no runs), and about a dozen tests read the committed ledger
rather than a fixture.

**Fixed.**
- `tests.yml` also runs daily at 15:40 UTC, after the nightly.
- The `clamped` assertion is now per row: `clamped` must equal what the raw score
  implies. That is stronger than "not always empty", and it is correct when nothing
  clamped.
- That change exposed an identity check that had never actually executed, because the
  test always failed before reaching it. The check assumed a 5e-4 reconstruction
  tolerance, but `perp_mult` is recorded at three decimals and `score()` multiplies the
  unrounded value. XMR ×0.922 missed by 0.036 on 09-18 with nothing wrong. The tolerance
  is now derived from each column's recorded precision.
- The forward leg-count ceiling in `test_ic_provenance` assumed contiguous nights. With
  the gap, 09-16 → 09-23 is a genuine seven-day leg. It is now bounded by the calendar
  span.

migration are now done, each with a test that fails on the previous code for the stated
reason.

| Item | What changed | Proof |

Defects found during the second pass, all fixed here:

- **A failed `signals.json` aborted `loadLedger()`** with a bare `return`, silently
  skipping `perp.json` and every other artifact — one missing file withheld the funding
  overlay and blanked the paper book, monitor and edge panels. Each is fetched on its own.
- **The drawer's recorded derivatives (`PERPS`) carried stale rows.** Each symbol kept
  its last row of *any* night, so a name that left the persisted top fifty showed weeks-old
  open interest and funding as tonight's — the stale-carry pattern AUDIT-PHASE1.5 retired
  from the overlay. Now the newest night only.
- **The drawer's "Score modifier" printed `funding.json`'s value** even when the score
  applied a different one (the overlay withheld — exactly the state production has been
  in since 09-18). It now shows the applied multiplier and names any disagreement, and
  never calls an absent reading "a neutral ×1.0, not a missing reading".
- **`rwa.degraded.json` was never staged**, though the Method page says a quarantined
  run's board is kept; with the new leftover guard such a night would have gone red and
  lost it. Both writers stage it.

## 5. Artifacts regenerated in this change

The derived artifacts that §1.3 and §1.1 had left wrong were regenerated from the
**committed** ledger, using the nightly's own functions. No new data was fetched.

- `market_breadth.json`: the edge block.
- `index.json`: the canonical edge.
- `walkforward.json`: 7 nights, 2026-09-15 → 2026-09-23.

An offline rebuild of `market_breadth.json` differs from the committed file only in the
edge figures and `generated_at`.

`perp.json` was **not** regenerated. It needs the live funding fetch, and rebuilding the
transport from a secondary record is the kind of substitution this repository refuses.
The first nightly after this merges writes it and, now, commits it. Until then the board
keeps withholding the overlay and says so, which is the correct degraded state.

## 6. Recorded for review — frozen surfaces, not changed

Two inconsistencies in the qualification and basket layer. Both change which names
qualify or how the basket ranks if "fixed", which this pass may not do; both are stated
in the code where they live and on the Method page, and neither moves `SPEC_HASH` by
being recorded.

1. **The terminal and the nightly qualify with different gates.** The terminal's
   QUALIFIED flag uses `computeLAVL` (gate C) and adds a proxy-ERA ≤ 1.5 condition (gate
   B); the nightly's `_conjunctive_gate`, whose docstring said it "replicates the
   front-end gated flag", uses `_lavl_regime` — a different formula — and no proxy-ERA
   term. On the real 2026-09-23 markets payload (250 names): the LAVL leg disagrees on
   **181 of 250**; the final verdict qualifies **2 names in the terminal and 9 in the
   nightly** (ARB, BONK, NEAR, OP, PEPE, UNI, WIF qualify only in the nightly). The board's
   "QUALIFIED n/N" and the basket's gated universe are therefore not the same set.
   `_lavl_regime` is a captured function, so reconciling toward it in the browser is a
   presentation change and reconciling the other way moves the hash.
2. **`build_basket` ranks without the funding multiplier** — it calls `score(t, None,
   btc)` — while the published conviction includes it. On 2026-09-23 only 13 of 235 rows
   carry a non-neutral multiplier and the top ten is identical either way, so the effect
   is latent today. The terminal's comment claiming the board used "the SAME leverage
   overlay as the nightly conviction-weighted index" was false and is corrected.

## 7. Still recommended

1. **Month-shard the RWA ledgers** (dedicated follow-up PR; design, affected surfaces,
   determinism proof, cutover and tests in `docs/DESIGN-RWA-SHARDING.md`).
   `rwa_wrappers.csv` is 5.1 MB, +342 KB a night; 50 MiB around 2027-02 at a constant
   rate (2026-12 if growth keeps accelerating) and GitHub's 100 MiB push limit around
   2027-07 (2027-02). Recommended to merge **before 2026-10-01**, while every row is in
   one month and the migration is a byte-identical rename, in a window with no nightly
   in flight.
2. **`signals.json`** (5.1 MB, +~100 KB a night; `rows` duplicates `signals.csv` cell for
   cell). Writing it minified is safe for every enumerated consumer and cuts 29.5% on
   disk; a rolling 14-night `rows` window plus a lazy `signals.csv` fetch for deep rewind
   is the real fix. Do **not** drop `rows` outright: rewind, the drawer, the per-symbol
   strategy/ATR/turnover maps and the nightly ATR gate read the full history. Consumer
   enumeration in the design doc, §6.
3. **A same-day manual re-run of the nightly fails the ATR gate** (documented in
   `rwa.py`). With the concurrency group, a dispatch queued behind a successful scheduled
   run goes red rather than committing — expected, and now recorded as such in
   `runs.csv`.
